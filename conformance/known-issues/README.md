# Oracle discrepancies and TS-only acceptance probes

These original source trees preserve oracle evidence. Matching acceptance scenarios now live in `scenarios/` with `targets: ["ts"]`, so oracle runs skip them and the TS implementation must fix them. All were investigated against the published 0.0.27 package on Farm 1.7.11 / Node 22.22.2.

- **`root-head-only`**: `root.tsx` exports a head but no default. Farm builds successfully; importing the output throws `ReferenceError: src_root_tsx_default is not defined`. The plan's reference claim `root?.default ?? DefaultRootHOC` is not true for this input. The passing head cases explicitly export `DefaultRootHOC`. The TS implementation should implement the documented fallback.
- **`head-star`**: a route uses `export * from "../../lib/head"`. The page renders `Root|Layout`, omitting the re-exported head, instead of `Root|Layout|Lib`. Explicit re-exports, imported aliases, destructuring and namespace exports pass. The broad review claim that every export form is recognized needs this exception. The TS-only scenario records the desired expectation.
- **`head-deep-mutation`**: a head function changes `prev.metas[0].content`. Two requests render `cx`, then `cxx`. This is the shallow-copy limitation already identified in plan Part 2; TS should render `cx` each time. The passing `head-isolation` scenario tests shallow title/array isolation only.
- **`m16`** (`agent-a661255d0075a9714.jsonl`, rv3 middleware probes): `export { mw as "default" }` aborts Farm with `non-ident exported is not supported when tree shaking`. Disabling host tree-shaking still aborts in the bundler analyzer. This is a Farm host failure, not an ordinary Recooler validation diagnostic. It is not accepted as a build-error test.
- **`m14`** (same transcript): a namespace object exported as default passes build-time export-name validation, then responds 500 (`handler is not a function`). The reference only promises that a default export exists; it does not validate callability.
- **`m15`** (same transcript): a class exported as default builds, then responds 500 because Hono invokes it as a handler without `new`. TS must reject classes as middleware even though `typeof` returns `function`, for example via the `class` prefix of `Function.prototype.toString.call(value)`.
- **`m17`** (same transcript): `declare const mw; export default mw` builds, then importing the output throws `mw is not defined`. There is no runtime declaration. Module evaluation fails before `createApp` can inspect the namespace, so a startup middleware/function diagnostic is unreachable. This source remains here as a known issue; it is not a runnable TS startup-validation scenario. A future load-error contract could require the failing module's path independently of the ReferenceError text.

The original `head-star` and `m16` JSON remains here for provenance. Runnable TS acceptance checks cover six discrepancies. `m14` and `m15` must return `buildError` during build/startup, with independent assertions for `routes/middleware.ts` on TS (`src/routes/middleware.ts` on Farm) and `must export a middleware function`, rather than responding 500 on a first request. A seventh TS-only scenario, `root-scripts`, exercises the root’s props.scripts URL array, route metadata and an actual client handler in emitted chunks.
